# SIPAPUA QR — Keputusan akhir arsitektur Rp0

**NO-GO untuk staging hosted dan produksi. GO untuk kandidat dan pengujian lokal.** Anggaran tambahan yang diizinkan dan digunakan adalah Rp0. Kebutuhan verifier privat yang aman tanpa billing belum dapat dipenuhi dengan infrastruktur yang terbukti tersedia. Hentikan jalur hosted sampai ada bukti baru untuk gate di bawah.

## Verifier dan pilihan arsitektur

Pemeriksaan artefak repositori dan dokumentasi publik tidak menemukan issuer workload tepercaya yang sudah tersedia untuk Worker SIPAPUA. Konfigurasi kandidat memiliki binding privat, tetapi tujuan layanan dan origin masih kosong. Audit lokal tidak dapat menetapkan apakah ada issuer yang tidak terdokumentasi di organisasi Owner. Cloudflare service binding membatasi pemanggil RPC. Google WIF memerlukan assertion dari issuer yang dipercaya Google, dengan ketentuan issuer, audience, subject dan kondisi atribut yang membatasi verifier. Google STS menukar assertion itu menjadi OAuth access token berumur pendek. Pilihan kedua adalah impersonasi identity staging khusus melalui IAM Credentials jika API target tidak menerima principal federasi langsung. Tidak ada role atau key yang dibuat. [Google WIF](https://docs.cloud.google.com/iam/docs/workload-identity-federation) · [Cloudflare RPC](https://developers.cloudflare.com/workers/runtime-apis/bindings/service-bindings/rpc/)

| Alternatif | Keputusan |
|---|---|
| Worker + verifier privat dengan issuer independen yang sudah tersedia, WIF dan OAuth berumur pendek | Rekomendasi jika Owner kemudian dapat membuktikan issuer dan semua API bekerja tanpa billing. Kedua syarat saat ini **BLOCKED**. |
| Verifier Node di host mandiri | Layak untuk emulator. Hosted tetap memerlukan host yang sudah dibiayai, transport privat, identitas workload tepercaya, operasional Rp0 tambahan dan OAuth Google yang sah. Belum ada prasyarat yang cukup untuk GO. |
| Firebase Functions atau Cloud Run | **NO-GO**. Membutuhkan Blaze atau akun Cloud Billing, termasuk Cloud Run Free Tier. |
| Verifikasi JWT dengan public keys | Pertahankan untuk signature, issuer, audience, expiry dan App ID. Status disabled/revoked, perubahan status owner dan konsumsi provider App Check tetap memerlukan layanan otoritatif. JWT publik saja ditolak sebagai pengganti verifier. |

Kredensial browser anggota (Firebase ID token, App Check token, klaim UID) hanya berlaku pada peran masing-masing dan tidak ditukar menjadi identitas layanan. Verifier perlu Auth account lookup dengan `firebaseauth.users.get` untuk memeriksa status disabled, akun hilang dan cutoff revocation terhadap `auth_time`; Firestore point reads dengan `datastore.entities.get` untuk profil/alokasi canonical owner; dan App Check consumption dengan OAuth serta `firebaseappcheck.appCheckTokens.verify`, yang termasuk dalam `roles/firebaseappcheck.tokenVerifier`. Browser tetap meminta limited-use token per operasi. Hanya keberhasilan sah pada konsumsi pertama yang boleh diterima. REST Google menghilangkan `alreadyConsumed` pada konsumsi pertama; SDK mengembalikan `false`. Perbedaan kontrak ini sudah diuji dengan mock RC-04A. Caller masih menggunakan bearer sendiri pada jalur akses dokumen sendiri melalui Rules. Token caller tidak memberi hak memeriksa akun pemilik kartu lain. [Auth revocation](https://firebase.google.com/docs/auth/admin/manage-sessions) · [Auth lookup API](https://docs.cloud.google.com/identity-platform/docs/reference/rest/v1/accounts/lookup) · [Firestore IAM](https://cloud.google.com/iam/docs/roles-permissions/firestore) · [App Check consume API](https://firebase.google.com/docs/reference/appcheck/rest/v1beta/projects/verifyAppCheckToken) · [Firebase plans](https://firebase.google.com/docs/projects/billing/firebase-pricing-plans) · [Cloud Billing](https://docs.cloud.google.com/docs/get-started/learn-about-billing)

Firebase Auth email/password dan Firestore Standard tersedia pada Spark tanpa billing. Browser App Check tetap menggunakan provider yang disetujui dan kuota attestation yang berlaku. Workers Free menyediakan 100.000 request per hari akun; D1 Free menyediakan 5 juta rows read dan 100.000 rows written per hari akun. Worker dan D1 Free memenuhi kriteria biaya dalam batas paket, sedangkan App Check consumption, Auth privileged lookup, dan owner Firestore reads dengan identitas federasi pada proyek tanpa billing belum dibuktikan. [Firebase pricing](https://firebase.google.com/pricing) · [reCAPTCHA quota](https://docs.cloud.google.com/recaptcha/quotas) · [Workers limits](https://developers.cloudflare.com/workers/platform/limits/) · [D1 pricing](https://developers.cloudflare.com/d1/platform/pricing/)

## Guard lokal dan estimasi SQL

Guard harian memakai dua baris ledger, satu untuk request dan satu untuk cleanup, dengan upsert kondisional atomik dan rollover UTC. Hari yang lebih lama tidak dapat menghapus pemakaian hari baru. Reservasi dilakukan setelah validasi request/credential lokal dan sebelum counter per menit, verifier atau mutasi kartu. Debit tidak dikembalikan setelah kegagalan karena request mungkin telah memakai kapasitas. SQL independen mempertahankan efek parsial counter sebagai debit konservatif. Tidak ada retry otomatis dalam kode Worker. Retry klien, timeout dengan hasil tidak diketahui, dan replay yang mencapai guard menghabiskan reservasi baru. Kartu hanya dikonsumsi dengan satu update kondisional. Tidak ada transaksi lintas D1 dan Firebase.

| Jalur | SQL Worker kandidat | Estimasi kerja SQLite sebelum metering D1 |
|---|---|---|
| Invalid, anonymous, origin/method ditolak, atau preflight | Tidak ada | 0 row writes/reads D1 |
| Kuota request harian penuh | 1 conditional upsert `qr_daily_budget` | Satu lookup keyed, 0 mutasi saat ditolak |
| Global cap penuh / UID cap penuh | Ledger + 1 / 2 conditional upsert `qr_budget` | 1 / 2 mutasi tabel, plus indeks pada insert counter global bila tepat. Sampai tiga lookup keyed |
| Verifier gagal / menolak | Ledger + 2 counter upsert | Hingga 3 mutasi tabel, dengan hingga 4 entri indeks pada dua insert counter. Tiga keyed probes |
| Issue atau rotasi | Ledger + 2 counter + conditional upsert `cards` | Hingga 4 mutasi tabel dan sekitar 7–10 operasi entri indeks dalam model konservatif; probe key UID/token dan counter. Cooldown tidak mengubah kartu |
| Lookup ditolak / sukses | Ledger + 2 counter + 1 token SELECT, ditambah conditional UPDATE jika owner valid | Hingga 3 / 4 mutasi tabel. Lookup memakai indeks token dan evaluasi row kartu. Update consumed_at tidak mengubah kolom indeks |
| Cleanup | Ledger cleanup + DELETE kedaluwarsa untuk dua tabel, masing-masing hingga 64 baris | Hingga 129 mutasi tabel, plus sekitar 320 penghapusan entri indeks (3 indeks kartu dan 2 indeks counter per baris). Dua pencarian rentang kedaluwarsa dan lookup row untuk delete |

Hitungan tersebut memisahkan operasi logis dari meter platform. D1 dapat menghitung lebih banyak reads akibat rencana query dan checks, serta indeks dan perubahan internal dapat memengaruhi writes. Tidak ada data hosted untuk menjamin batas. Guard memperkirakan **32 kredit/request, maksimum 32.000 per hari (1.000 admission)**. Cleanup **600 kredit/run, maksimum 30.000 per hari**. Cron contoh tiap 30 menit memakai 28.800 kredit jika seluruh 48 run dijalankan. Sisa 38.000 row writes merupakan headroom desain pada akun khusus. Request yang ditolak masih bisa memakai row reads serta Worker quota. Pantau kedua meter; baca metrik `meta.rows_read` dan `meta.rows_written` setiap jalur termasuk indeks, overhead maintenance dan operasi yang melewati tengah malam. Kuota D1 adalah per akun, jadi pemakaian lain dapat mengurangi headroom.

Saat kuota aplikasi habis, issue/lookup mengembalikan `429` sebelum verifier atau operasi kartu. Saat quota/provider D1 gagal, HTTP mengembalikan `503` tanpa bypass atau membocorkan error internal. Cleanup berhenti ketika reserve cleanup habis, dan kegagalan D1 pada scheduled handler dapat dicatat sebagai kegagalan cron tanpa merekam payload. Token kedaluwarsa tetap ditolak sebelum dan selama konsumsi meski purge tertunda. Cron 30 menit membuat target cleanup 10 menit RC-03 tidak berlaku pada kandidat ini. D1 Time Travel Free mempertahankan riwayat tujuh hari; reset token lama sebelum membuka scan setelah restore. [D1 biaya dan indeks](https://developers.cloudflare.com/d1/platform/pricing/) · [D1 hard quota](https://developers.cloudflare.com/d1/platform/release-notes/) · [Time Travel](https://developers.cloudflare.com/d1/reference/time-travel/)

## Verifikasi dan gate pembukaan kembali

- **17 PASS, 0 FAIL baru** melalui Worker kandidat dengan SQLite serta Auth, App Check, dan ingress sintetis. Mencakup race admission pada kredit terakhir, UTC rollover, penolakan hari lampau, storage failure pada issue/lookup, dan isolasi kuota cleanup. Regresi token, authorization, replay dan adapter ikut lulus. Jalankan `node --test candidates/qr-zero-cost-final/test/worker.test.mjs`.
- **11 PASS, 0 FAIL pada RC-04A** digunakan sebagai bukti sebelumnya, terdiri dari 7 Firebase Auth/Firestore emulator dan 4 SQLite/mock. Tidak ada perubahan kontrak Rules atau verifier yang memerlukan pengulangan suite itu.
- **3 gate BLOCKED**: issuer/OAuth dan izin minimum tanpa billing; bukti Auth revocation/current owner serta App Check consumption hosted tanpa billing; pengukuran meter D1/Worker Free dengan cadangan cleanup. Tidak ada Google atau Cloudflare hosted test.

Deployment hanya dapat direncanakan setelah Owner menyetujui bukti Rp0, semua gate di atas lulus pada proyek sintetis terisolasi, dan browser/QR fisik serta rollback disetujui. Gunakan kuota Free yang tetap, schema D1 baru, issuer terverifikasi, dan referensi Rules staging dalam paket RC-03. Sampai saat itu, registrasi HOLD, QR maintenance ACTIVE dan QR friendship DISABLED. Tidak ada perubahan production, Rules aktif, IAM, billing, deployment, commit, push, atau merge.
